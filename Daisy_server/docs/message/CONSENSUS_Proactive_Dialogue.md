# CONSENSUS: 陪伴式AI主动对话机制

## 1. 最终需求共识

### 1.1 核心目标
构建一套主动对话系统，使 Daisy 能够基于时间、事件和用户状态，主动向用户发起有意义的对话，从而提升“陪伴感”。

### 1.2 范围界定 (In-Scope)
- **时间驱动触发**: 支持 Cron 风格的定时检查（如每日早安、晚安）。
- **活跃检测触发**: 基于用户最近一次交互时间的检测。
- **智能内容生成**: 使用 LLM 根据用户画像和历史记录生成开场白。
- **实时推送**: 利用现有的 SSE (Server-Sent Events) 通道推送消息给在线用户。
- **自适应防打扰系统**: 
    - **自适应作息感知**: 系统自动学习用户的活跃时间分布，仅在用户习惯活跃的时段发起对话，替代固定的“勿扰模式”。
    - **每日上限**: 限制每天主动发起的最大次数（如 3 次）。
    - **智能退避**: 如果用户忽略主动消息，自动延长下次触发间隔。
    - **冷启动策略**: 对新用户使用默认作息模板，随交互积累逐渐切换到个性化模型。

### 1.3 范围排除 (Out-of-Scope)
- **离线推送**: 暂不接入移动端 Push Notification (FCM/APNs) 或邮件推送，仅限 Web 端在线推送。
- **复杂多模态主动**: 主动发送的消息目前仅限文本，不包含图片或语音。

## 2. 技术实现方案

### 2.1 架构选型
确认采用 **混合驱动架构**：
- **触发器**: `APScheduler` (运行在 FastAPI 进程中，负责轻量级定时信号)。
- **执行器**: `arq` (Redis 队列 Worker，负责重逻辑：状态检查、LLM 生成)。
- **通信通道**: Redis Pub/Sub -> FastAPI SSE。

### 2.2 关键技术决策
| 决策点 | 方案 | 理由 |
| :--- | :--- | :--- |
| **状态存储** | Redis | 高频读写用户状态（在线/离线、上次交互时间），TTL 自动过期，性能最优。 |
| **冷却控制** | Redis + 算法 | 结合 TTL (硬冷却) 和 Counter (每日计数/连续忽略计数) 实现动态策略。 |
| **作息学习** | Redis Hash | 使用 `user:{id}:activity_stats` 记录 24 小时每个时段的交互频次，计算活跃概率。 |
| **情感记忆** | Redis Hash | 缓存用户最近一次显著的情感状态 (`user:{id}:last_emotion`)，作为打破常规冷却的依据。 |
| **打扰判定** | 双轨制 (Dual-Track) | **常规轨道**: 严格遵循作息规律；**情感轨道**: 识别到 Emo 状态时，豁免作息限制，优先关怀。 |
| **用户感知** | SSE 连接状态 | 通过监听 Redis Pub/Sub 的订阅者数量或心跳来判断用户是否在线。 |

## 3. 验收标准
1.  **功能验证**:
    - 配置一个每分钟触发的任务（测试用），用户在前端能收到消息。
    - 连续触发时，受冷却机制限制，不重复发送。
2.  **性能验证**:
    - 调度器运行不阻塞主线程 API 响应。
3.  **体验验证**:
    - 主动消息在前端正确显示，不破坏现有对话流。

## 4. 风险与缓解
- **风险**: LLM 生成成本过高。
- **缓解**: 在调用 LLM 前增加规则层过滤（如：用户刚说过话，直接跳过），减少无效调用。
