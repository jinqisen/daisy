# ALIGNMENT: 主动对话机制需求对齐

## 1. 原始需求分析
用户希望 Daisy 具备“主动性”，不再是被动问答机器。
但同时提出了强烈的“防打扰”诉求：
1.  **避免过度打扰**: 不希望像推销短信一样狂轰滥炸。
2.  **个性化作息**: 不希望用硬编码的时间窗口（如 9:00-21:00），而是基于用户的实际作息习惯。
3.  **情感关怀优先**: 在用户情绪低落（Emo）时，应该突破常规限制，给予关怀。

## 2. 关键决策点 (Decision Points)

### DP1: 如何判断“何时打扰是合适的”？
- **选项 A**: 固定时间窗口 (9am - 9pm)。
    - *缺点*: 对夜猫子用户不友好，对早起用户不及时。
- **选项 B**: 用户手动设置。
    - *缺点*: 增加配置负担，不够智能。
- **选项 C (Selected)**: **自适应作息学习 (Adaptive Learning)**。
    - *方案*: 记录用户历史活跃时间分布 (Histogram)，计算当前小时的活跃概率 $P(active|hour)$。仅在 $P > Threshold$ 时尝试发起。

### DP2: 如何平衡“不打扰”与“及时关怀”？
- **冲突点**: 用户深夜 Emo，按作息逻辑不该打扰，但按关怀逻辑应该安抚。
- **决策 (Selected)**: **双轨门控机制 (Dual-Track Gatekeeper)**。
    - **Track A (Routine)**: 常规陪伴。严格受限于作息概率、每日次数上限、冷却时间。
    - **Track B (Emotional)**: 情感急救。当检测到强负面情绪（Sadness/Lonely > 0.6）时，**豁免**作息限制和部分冷却限制，优先发起关怀。

### DP3: 如何避免“尬聊”？
- **决策**: 引入 **LLM 决策层 (Evaluation Step)**。
    - 在通过门控后，不直接发送，而是将上下文喂给 LLM，询问：“现在发起对话合适吗？有话可说吗？”
    - 只有 LLM 打分高 (Score >= 8) 且生成了由意义的内容，才真正发送。

## 3. 约束与边界
- **仅限在线用户**: 目前仅对 Web 端在线（SSE 连接中）的用户发起，暂不涉及离线推送（Push Notification）。
- **数据隐私**: 作息数据仅存储统计值（小时维度的计数），不存储具体活动内容。
- **频率限制**: 默认每日 3 次主动发起上限（情感豁免可 +1）。

## 4. 最终共识
系统将实现一个 **“基于作息感知与情感优先的双轨主动对话系统”**。
核心原则：**平时不打扰，难过有回应。**
