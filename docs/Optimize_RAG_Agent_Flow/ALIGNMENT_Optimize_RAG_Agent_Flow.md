# 任务：优化 RAG 与 Agent 的交互流程

## 1. 项目上下文分析

当前 `Daisy_brain` 模块处理聊天请求的流程如下 (`src/api/chat.py`):
1.  接收用户消息。
2.  调用 `LightRAGManager.query(user_content)` 获取上下文 (`context`)。
    - 注意：LightRAG 的 `query` 方法通常会基于检索到的片段生成一段综合性的回答（Answer），而不仅仅是原始片段。
3.  构建系统提示词 (`_build_immersive_system_prompt`)，将 `context` 作为“你记得的小说事实”注入。
4.  调用 LLM (`gpt_4o_mini_stream`) 生成最终回复。

**问题**: 
用户指出回复“像直接通过 RAG 回答”，即回复内容虽然准确，但缺乏角色个性（Li Persona），语气生硬或过于陈述性。这是因为 LightRAG 生成的 `context` 本身往往是一个完整的陈述性回答，LLM 在生成时倾向于直接复述或微调这个高质量的“事实”，导致角色人设被覆盖。

## 2. 需求理解确认

### 原始需求
> "你是不是直接通过rag就回答了。这个不对，应该是rag检索相关信息，塞到AI智能体，让AI智能体回答，回答需要符合人物档案。"

### 核心目标
1.  **解耦检索与回答**: RAG 仅负责提供“知识/素材”，而非“答案”。
2.  **强化 Agent 人设**: Agent 需要“消化”检索到的信息，结合自身性格、经历、说话风格（语气词、口癖等）重新组织语言。
3.  **沉浸感**: 回复必须是第一人称，符合角色当下的心理状态。

## 3. 智能决策策略

### 方案 A: 修改 RAG 返回格式 (Backend Tweak)
尝试让 LightRAG 返回原始片段 (Chunks) 而非生成的 Answer。
- *优点*: 素材更原始，LLM 发挥空间大。
- *风险*: 原始片段可能太长或包含无关信息，增加上下文窗口压力；LightRAG 封装可能较深，修改成本未知。

### 方案 B: 提示词工程 + 思维链 (Prompt Engineering)
在 System Prompt 中强制引入“思考-转化”步骤。
- 要求 Agent 先在内心（或隐藏的 Thought 块）分析 RAG 提供的知识。
- 明确 RAG 上下文是“枯燥的资料库”，必须用“角色的嘴”说出来。
- 引入 `<thought>` 标签引导模型先思考后回答。

### 方案 C: 两阶段生成 (Pipeline Change)
1. RAG 检索知识。
2. (新增) 知识重写：调用一次 LLM 将 RAG 结果转化为简短的“记忆点”。
3. 角色生成：将“记忆点”输入给角色 LLM。
- *缺点*: 增加延迟和成本。

**决策**: 优先采用 **方案 B (Prompt Engineering + CoT)**。
这是最快且最有效的手段，不需要大幅改动底层 RAG 逻辑，且能显著提升沉浸感。如果 LightRAG 支持 `only_context` 模式，结合方案 A 效果更好。

## 4. 待确认问题
无。需求非常明确。

## 5. 验收标准
1.  **风格一致性**: 回复必须符合李家角色的语气（如：沉稳、家族荣誉感、特定的称呼）。
2.  **信息准确性**: 能够准确回答关于“青灰色鉴子”等事实，但不能像读百科全书。
3.  **无 RAG 味**: 避免“根据资料显示”、“检索结果如下”等机械表达。
